>
> **文档性质**：需求基线 + 架构设计 + 版本路线图 + 验收标准 + 面试/简历材料。

> **时间基准**：不以固定日历天数为约束。路线图以 **9 个阶段 / 36 周（全职）** 为完整范围，并提供 3 / 5 / 8 个月裁剪方案。

# 第一部分 需求与范围

## 一、项目概述与能力定位

### 1.1 项目要解决什么问题

企业在密钥与证书管理上面临四类问题：

| 问题 | 典型表现 | 本项目的应对 |
|---|---|---|
| 密钥散落 | 密钥硬编码、明文入库、无轮换 | 集中托管 + 加密落库 + 强制轮换 |
| 证书失控 | 到期不知、吊销无记录、签发随意 | 完整证书生命周期 + 受控 Profile + CRL |
| 调用不规范 | 算法参数各异、IV 复用、无用途隔离 | 统一密码服务 API + 参数固定 + 用途校验 |
| 审计缺失 | 谁用了哪把密钥无从查证 | 防篡改审计 + 权限最小化 |

### 1.2 能力定位

```text
                    企业密码基础设施
                            |
        +-------------------+-------------------+
        |                                       |
   密钥管理 (KMS)                        证书管理 (PKI)
   - 密钥生命周期                        - CA 层级
   - 加密存储与保护                       - CSR / 签发 / 吊销
   - 版本与轮换                          - CRL / OCSP
   - 信封加密                            - Profile 受控签发
   - BYOK / 导出托管                     - 信任库与验证
        |                                       |
        +-------------------+-------------------+
                            |
                     密码运算服务
              加解密 / 签名验签 / 摘要 / HMAC / 随机数
                            |
        +-------------------+-------------------+
        |                   |                   |
   协议互操作          多租户与策略         工具链与生态
   KMIP/EST/ACME      租户隔离/ACL         CLI/SDK/UI/K8s
   PKCS#11/GMTLS      配额/双人授权         Agent/CSI/Operator
```

### 1.3 设计原则

1. **不自己造密码**：算法一律调用 OpenSSL/GmSSL，工程的难点在密钥体系、格式、权限、审计与交付；
2. **数据库不可信**：所有密钥材料加密落库，拖库不致命；
3. **分层保护**：Seal Key → Master Key → Managed Key → DEK，职责不混用；
4. **显式优于默认**：算法、版本、编码、SM2 User ID 全部显式记录，不依赖库默认值；
5. **能力可探测**：Provider 能力通过接口查询，不假设所有后端一致；
6. **失败关闭**：审计失败、策略无法判定时，拒绝操作而非放行；
7. **可演进**：格式带版本号，schema 可迁移，协议可增量接入。

### 1.4 适用岗位方向

| 方向 | 项目可证明的能力 |
|---|---|
| 密码产品研发 | Provider 抽象、密码设备对接、算法参数治理 |
| 密码服务平台 | 密钥/证书全生命周期、审计、多租户 |
| 密码设备/密码机 | PKCS#11/SDF、私钥不可导出、设备容错 |
| 安全平台/基础架构 | 协议互操作（KMIP/EST/ACME）、高可用、生态集成 |
| 密码合规咨询 | 密评/等保对照、算法清单、密钥仪式文档 |

### 4.2 OpenSSL 与 GmSSL 集成策略（关键决策）

**问题**：两个库可能导出同名符号、头文件定义冲突、SM2 默认 User ID 与 OID 行为不一致、内存分配器与错误栈互相干扰。

**决策**：GmSSL 以**独立进程**提供服务。

```text
KeyCertHub 主进程（链接 OpenSSL）
        |
   gRPC / Unix Socket
        |
GmSSL Provider Service（独立进程，链接 GmSSL）
```

**收益**：

- 彻底避免符号与 ABI 冲突；
- 崩溃隔离；
- 天然模拟"密码设备在进程外"的真实形态；
- 与 PR-13（远程 Provider）设计一致，后续可平滑替换为真实密码机。

**备选**（时间紧张时）：两个独立构建目标，编译期选择，不在运行时混用。

### 5.2 分层职责与禁止事项

| 层 | 职责 | 禁止 |
|---|---|---|
| 接入层 | 协议适配、参数解析 | 不含业务逻辑 |
| 网关层 | 认证、授权、限流、审计前置 | 不直接访问数据库 |
| 应用层 | 业务编排、事务边界 | 不保存裸 `EVP_PKEY*` |
| 领域层 | 状态机、策略、版本规则 | 不依赖 HTTP/DB 实现 |
| Provider | 算法、格式、设备差异 | 不做业务判断 |
| 存储层 | 持久化与查询 | 不做密码运算 |

### 5.3 六条不可违反的规则

1. Controller 不直接调用 OpenSSL/GmSSL；
2. Service 只持有 `KeyHandle` / `SecureBuffer`，不持有裸密码库对象；
3. Domain 层不依赖 HTTP 与数据库实现；
4. 所有私钥与对称密钥落库前必须加密；
5. 敏感操作必须经过 认证 → 授权 → 策略 → 审计 四步；
6. 跨租户访问一律拒绝并记录审计。

### 5.4 关键数据流

**加密**：

```text
Client → 网关(鉴权/租户/限流) → CryptoService
       → KeyManager(取 KeyHandle + 状态/用途/版本校验)
       → Provider(执行加密) → AuditService(记录) → Envelope
```

**密钥创建**：

```text
Client → KeyService → Provider(生成)
       → Seal/MasterKey(加密材料) → Repository(存元数据+密文)
       → Audit → Client
```

**证书签发**：

```text
Client → CertificateService → CSR 校验 → Profile 策略校验
       → KeyManager(取 CA KeyHandle) → Provider(签名)
       → Repository(存证书) → Audit → 证书 + 链
```

**动态凭据**：

```text
Client → SecretService → 校验租约策略 → 后端(DB/云/SSH)
       → 生成短期凭据 → 创建租约 → Audit → 凭据 + lease_id
```

### 5.5 信任边界

| 边界 | 信任级别 | 说明 |
|---|---|---|
| Client → 接入层 | 不信任 | 必须认证与校验 |
| 进程内各层 | 信任 | 参数已校验 |
| Provider 进程 | 有条件信任 | 需 TLS/mTLS + 输入校验 |
| 数据库 | **不信任** | 视为可被拖库 |
| 备份存储 | **不信任** | 备份包必须加密 |
| 审计文件 | 不信任 | 需 Hash Chain |
| KMS/HSM | 信任但需容错 | 可能超时/不可用 |

## 六、分层密钥保护设计

### 6.1 四层密钥体系

```text
Level 0  Seal Key
  来源：dev-file / Mock HSM / 口令派生 / Shamir 分片 / 云 KMS
  作用：解封 Master Key
        |
        v
Level 1  Master Key (Root KEK)
  存储：加密后落库
  作用：加密所有 Managed Key 材料
        |
        v
Level 2  Managed Keys (KEK / DEK / 签名密钥 / CA 私钥)
  存储：元数据明文 + 材料密文
  作用：业务加解密、签名、包装 DEK
        |
        v
Level 3  Per-request DEK
  存储：随业务密文保存 Wrapped 形式
  作用：加密实际业务数据
```

**为什么必须分层**：Master Key 生命周期长（年）、使用频率低、权限最高；DEK 生命周期短（单次）、使用频率高。混用会导致密钥暴露面扩大且无法轮换。

### 6.2 Seal 状态机

```text
    启动
     |
     v
 +---------+  unseal(正确 Seal Key)  +-----------+
 | SEALED  | ----------------------> | UNSEALED  |
 +---------+                         +-----------+
     ^                                     |
     |         seal() / 重启 / 存储致命错误  |
     +-------------------------------------+
```

**SEALED 允许**：`/health`、`/seal/status`、`/seal/unseal`、`/version`。

**SEALED 禁止**：读取密钥材料、加解密、签名、证书签发、轮换、销毁。

**租户级 Seal**（V3）：单个租户可独立封存，不影响其他租户。

### 6.3 Seal 实现模式

| 模式 | 用途 | 安全等级 | 版本 |
|---|---|---|---|
| dev-file | 开发测试 | 低 | V1 |
| mock-hsm | 演示 HSM 语义 | 中 | V1 |
| password | 口令 + Argon2id 派生 | 中 | V2 |
| shamir | 多分片手动解封 | 高 | V2 |
| kms / transit | 云 KMS 或外部 KMS 自动解封 | 高 | V2 |

**硬性要求**：

- Seal Key 不写入代码、不提交 Git、不进日志；
- Master Key 仅在解封后驻留内存；
- Seal 时清理 Master Key 与所有缓存密钥；
- 进程退出清理敏感内存；
- 解封失败次数限制与告警。

### 6.4 密钥材料落库格式

```json
{
  "format_version": 1,
  "wrapping_algorithm": "AES-256-GCM",
  "master_key_version": 1,
  "nonce": "base64...",
  "ciphertext": "base64...",
  "tag": "base64..."
}
```

**AAD 绑定不可变元数据**：

```text
AAD = key_id ‖ key_version ‖ algorithm ‖ purposes ‖ tenant_id
```

**作用**：阻止攻击者把一条密钥密文搬移到其他 Key ID / 版本 / 租户之下，绕过策略或造成密钥混用。AAD 不匹配则 GCM 认证失败。

### 6.5 Master Key 轮换

```text
1. 生成 Master Key v2
2. 用 Seal Key 加密 v2 并落库
3. 开启双写窗口：新写入使用 v2
4. 后台逐步重加密所有存量密钥材料（v1 → v2）
5. 全部完成后标记 v1 为 retired
6. 记录轮换审计与进度指标
```

**要求**：轮换可中断可续跑（记录进度游标）；轮换期间两种版本均可解密。

### 6.6 敏感内存管理

```cpp
class SecureBuffer {
public:
    SecureBuffer() = default;
    explicit SecureBuffer(std::size_t size);
    ~SecureBuffer();

    SecureBuffer(const SecureBuffer&) = delete;
    SecureBuffer& operator=(const SecureBuffer&) = delete;
    SecureBuffer(SecureBuffer&&) noexcept;
    SecureBuffer& operator=(SecureBuffer&&) noexcept;

    std::span<std::uint8_t> bytes();
    std::size_t size() const noexcept;

private:
    std::unique_ptr<std::uint8_t[]> data_;
    std::size_t size_ = 0;
};
```

补充措施：

- `mlock` 防止换页（受 RLIMIT_MEMLOCK 限制时降级并告警）；
- 禁用 core dump（`setrlimit(RLIMIT_CORE, 0)`）；
- 日志格式化器拒绝输出 SecureBuffer；
- 析构使用 `OPENSSL_cleanse`。

**诚实边界**：编译器优化、内存分页、崩溃转储等因素使"绝对清除"无法承诺。文档需说明这一限制，而非过度承诺。

### 7.5 版本管理

```text
Key: payment-data (tenant: acme)
  latest_version      = 3
  min_encrypt_version = 3
  min_decrypt_version = 1

v1 RETIRED  ← 可解密历史
v2 RETIRED  ← 可解密历史
v3 ACTIVE   ← 加密/签名使用
```

**规则**：

1. 新加密/签名使用最新 ACTIVE 版本；
2. 密文与签名必须携带 `key_id` + `key_version`；
3. 旧版本保留 DECRYPT/VERIFY；
4. 低于 `min_decrypt_version` 拒绝（`KEY_VERSION_TOO_OLD`）；
5. `min_encrypt_version` 强制新数据用新密钥；
6. 轮换在事务内完成，并发用 CAS 保护；
7. 同一逻辑密钥最多一个 ACTIVE 版本；
8. 销毁清除材料，保留元数据与审计。

**触发条件**：三者中先满足者。后台任务扫描 `next_rotation_at`。

## 八、算法与参数约束

### 8.1 AES-256-GCM

```text
Key 32 字节 | Nonce 12 字节 | Tag 16 字节 | AAD 可选
```

规则：

- Nonce 由 CSPRNG 生成，禁止可预测计数器；
- 同一密钥下严禁 Nonce 重复（可导致认证密钥恢复）；
- 解密先验 Tag 再返回明文；
- Tag 失败统一 `CRYPTO_AUTH_FAILED`，不区分密钥错/密文坏；
- 完整 AAD 不入审计日志，仅记 `aad_hash`；
- 单密钥加密次数监控，接近阈值强制轮换。

### 8.2 SM4

```text
首选：SM4-GCM（Provider 支持时）
基线：SM4-CBC + HMAC-SM3（Encrypt-then-MAC）
```

CBC 模式要求：

- 禁止裸 SM4-CBC；
- 加密密钥与 MAC 密钥独立生成；
- `MAC = HMAC-SM3(mac_key, version ‖ algorithm ‖ iv ‖ aad ‖ ciphertext)`；
- 先验 MAC 再解密；
- Padding 错误与 MAC 错误对外返回同一错误；
- MAC 比较使用恒定时间函数。

### 8.3 RSA

```text
加解密   RSA-OAEP + SHA-256 + MGF1-SHA256
签名验签 RSA-PSS + SHA-256 + MGF1-SHA256
Salt     = Hash 长度（32 字节）
最小长度 2048（推荐 3072）
```

禁止：裸 RSA 加密、新功能使用 PKCS#1 v1.5 加密、用 RSA 直接加密大文件、依赖库默认参数。

### 8.4 ECDSA / Ed25519

```text
ECDSA：P-256 / P-384 / P-521，摘要 SHA-256/384/512
Ed25519：EdDSA，无独立摘要参数
签名编码：ASN.1 DER（默认），可支持 Raw r‖s
```

### 8.5 SM2

必须显式处理：

1. **摘要**：SM3，不得使用 SHA-256；
2. **User ID**：默认 `1234567812345678`，但必须显式记录并参与计算；
3. **签名格式**：ASN.1 DER 或 Raw `r‖s`，显式标注；
4. **公钥点编码**：压缩/非压缩明确指定。

```text
ZA = SM3(ENTL ‖ ID ‖ a ‖ b ‖ xG ‖ yG ‖ xA ‖ yA)
e  = SM3(ZA ‖ M)
签名 = SM2_Sign(e, d)
```

**跨库验签失败四大原因**：User ID 不一致、签名编码不同、公钥点编码不同、是否预哈希不一致。

**约束**：SM2 加密仅用于短数据或密钥材料。

### 8.6 抗量子（V3）

```text
ML-KEM-768（原 Kyber）：密钥封装
ML-DSA-65（原 Dilithium）：签名
混合模式：经典 + PQC 双证书/双签名，保证过渡期兼容
实现来源：liboqs 或 OpenSSL 3.5+ 内建 PQC
```

### 8.7 摘要与 MAC

```text
支持：SHA-256/384/512、SM3、HMAC-SHA256、HMAC-SM3
```

禁止：普通 Hash 代替 HMAC；`SHA256(password)` 存口令（应用 Argon2id）；自创 MAC 构造。

## 十、PKI 与证书管理设计

### 10.1 CA 层级

```text
Offline Root CA（演示用；生产应离线或存 HSM）
        |
        v
Online Intermediate CA
        |
        +-- TLS Server
        +-- TLS Client
        +-- Code Signing
        +-- Device / IoT
        +-- SM2 Signing / SM2 Encryption（双证书）
```

**生产约束**（文档必须写明）：Root CA 离线或 HSM 托管；Intermediate 才能在线；本项目演示环境允许软件 Root，但不得用于生产。

### 10.2 证书 Profile

```cpp
struct CertificateProfile {
    std::string profile_id;
    std::set<KeyAlgorithm> allowed_algorithms;
    std::chrono::days max_validity;
    bool is_ca = false;
    std::uint32_t path_len_constraint = 0;
    KeyUsage key_usage;
    ExtendedKeyUsage extended_key_usage;
    SanPolicy san_policy;
    bool allow_wildcard_san = false;
    bool require_san = true;
    std::string subject_template;
    std::set<std::string> required_subject_fields;
    std::vector<std::string> certificate_policies;   // OID
    NameConstraints name_constraints;                // V2
};
```

**Profile 必须拒绝**：普通证书请求 `CA=true`；超范围 SAN/通配符；超长有效期；KU/EKU 冲突；算法不在白名单；Subject 缺必填字段。

### 10.3 证书状态机

```text
REQUESTED → ISSUED → EXPIRED
                 → REVOKED
                 → SUPERSEDED（被续期/重签替代）
```

### 10.4 签发流程

```text
1. 生成或选择系统托管密钥（或使用 CSR 内公钥）
2. 创建或导入 PKCS#10 CSR
3. 验证 CSR 自签名
4. Profile 校验 Subject/SAN/KU/EKU/有效期
5. CSPRNG 生成唯一序列号（≥64 bit 熵，保证不重复）
6. Intermediate CA 私钥签名
7. 持久化证书元数据
8. 输出证书 PEM/DER 与完整链
9. 写审计
```

### 10.5 续期与重签（PK-11 / PK-12）

```text
续期（renew）：同一密钥，新有效期，新序列号
  → 旧证书标记 SUPERSEDED，新证书 renewed_from_id 指向旧证书

重密钥（rekey）：新密钥 + 新有效期
  → 保留 Subject/SAN/Profile，旧证书 SUPERSEDED
```

**要求**：续期前校验旧证书状态与 Profile 是否仍有效；续期生成新序列号；不能延长超过 Profile 的 `max_validity`。

### 10.6 验证流程

```text
1. DER/PEM 可解析
2. 用服务端信任库构建签名链（拒绝调用者传入任意根）
3. 时间在 not_before ~ not_after 内（含链上所有证书）
4. Hostname/SAN 匹配（如指定）
5. Key Usage / EKU 符合用途
6. Basic Constraints 正确（CA 标志、Path Length）
7. Name Constraints 满足（V2）
8. 不在 CRL 且 OCSP 非 revoked
9. 中间证书有效期覆盖
```

### 10.7 吊销与 CRL

吊销原因（RFC 5280）：

```text
unspecified | keyCompromise | cACompromise | affiliationChanged
superseded | cessationOfOperation | certificateHold | removeFromCRL
privilegeWithdrawn | aACompromise
```

CRL 要求：

- CRL Number 单调递增；
- `thisUpdate` / `nextUpdate` 明确；
- CA 私钥签名；
- PEM / DER 双格式；
- 吊销幂等；
- 已吊销不可恢复（`removeFromCRL` 需显式权限与审计）；
- 非签发 CA 不得吊销；
- Delta CRL 带 `deltaCRLIndicator` 扩展（V2）。

### 10.8 信任库管理（PK-22）

```text
信任库条目：根证书 + 用途（ca / client-mtls）+ 指纹
验证时只允许使用本库中的根
支持启用/禁用/删除，全部操作审计
指纹（SHA-256）唯一，防止重复导入
```

## 十一、协议互操作设计

### 11.1 KMIP 服务端（PT-01）

```text
支持操作：Create / Register / Get / Locate / Activate / Revoke
          Destroy / GetAttributes / Encrypt / Decrypt / Sign / Verify
```

### 11.2 EST（RFC 7030，PT-02）

```text

      /.well-known/est/simpleenroll  首次注册
      /.well-known/est/simplereenroll 续期
认证：mTLS（推荐）或 HTTP Basic + OTP
编码：PKCS#10 / PKCS#7
```

### 11.3 ACME（RFC 8555，PT-03）

```text
目录：/acme/directory
账户：new-account / new-order
挑战：http-01 / dns-01（tls-alpn-01 可选）
签发：finalize → 下载证书链
```

**价值**：可与 cert-manager、Traefik、Nginx 等自动续期生态直接集成（TL-12）。

### 11.4 OCSP（PT-05）

```text
请求：DER 编码 OCSP Request
响应：signed OCSP Response，含 producedAt、nextUpdate
签名：OCSP Responder 证书（可由 CA 签发）
缓存：响应缓存与 nonce 支持
```

### 11.5 PKCS#11 / SDF / SKF（PR-07 / PR-08）

```text
PKCS#11：国际接口，对接主流 HSM
SDF：国密密码设备接口规范
SKF：智能密码钥匙接口
共同语义：
  - 会话登录 / 会话池
  - 密钥句柄，私钥不可导出
  - 设备内签名与解密
  - 设备错误码映射到内部错误
  - 设备超时、掉线、重连
```

### 11.6 GMTLS 网关（PT-12）

```text
双证书：签名证书 + 加密证书
密码套件：ECC_SM4_SM3 等
作用：为不支持国密的客户端提供国密接入代理
```

### 11.7 协议接入通用要求

无论何种协议，接入层必须统一收敛到内部领域模型：

```text
协议报文 → 协议适配器 → 内部 Request → 网关(鉴权/限流/审计)
        → Service → Domain → Provider
```

禁止协议适配器绕过网关直接调用 Service。

```text
到期自动撤销
支持按前缀批量撤销（撤销树）
撤销必须调用后端清理（如删除数据库账号）
```

### 13.3 动态凭据（DS-07 ~ DS-09）

```text
数据库凭据：
  1. 连接目标数据库（管理员凭据来自配置，加密存储）
  2. 创建临时账号与随机口令
  3. 创建租约，绑定撤销回调
  4. 返回凭据 + lease_id
  5. 租约到期 → 删除账号

云凭据：调用云 STS 生成临时凭据，租约绑定回收
SSH 证书：用 SSH CA 签发短期证书，绑定 principals 与 TTL
```

**安全要求**：管理员凭据不落日志；临时口令用 SecureBuffer 处理；后端连接池与超时控制；撤销失败重试并告警。

### 13.4 响应包装（DS-05）

```text
wrapping token → 一次性、短 TTL、可限定使用次数
用于安全传递秘密，避免明文经过不可信通道
```

## 十四、高可用与灾备设计

### 14.1 可用性架构（OP-17）

```text
        +-----------------+
        |   Load Balancer |
        +--------+--------+
                 |
     +-----------+-----------+
     |                       |
+----v-----+          +------v---+
| Active   |  <---->  | Standby  |
| Node     | 心跳/转发 | Node     |
+----+-----+          +------+---+
     |                       |
     +-----------+-----------+
                 |
        +--------v---------+
        |  PostgreSQL 主备  |
        |  (Streaming Rep.) |
        +------------------+
```

**要点**：

- 领导者选举：利用 PostgreSQL 咨询锁或 advisory lock，不自研共识；
- Standby 只读，写请求转发至 Active；
- 缓存失效：写入后广播失效（LISTEN/NOTIFY 或轮询索引）；
- 节点必须各自 Unseal（Shamir 模式）；
- 脑裂保护：租约与 fencing token。

### 14.2 备份与恢复（OP-05 ~ OP-07）

| 对象 | 方式 | 加密 |
|---|---|---|
| 数据库 | PostgreSQL 物理/逻辑备份 | 传输与静态加密 |
| 密钥材料 | 加密备份包（KM-05） | 独立口令/KEK 包装 |
| 系统配置 | 配置文件版本化 | 含敏感项需加密 |
| 审计日志 | 归档 + 链证明 | 只读归档 |

**恢复演练**：每阶段至少一次完整恢复演练并记录耗时（OP-20）。

### 14.3 灾难恢复目标

```text
RPO（可容忍数据丢失）：≤ 5 分钟
RTO（恢复时间目标）：≤ 1 小时
关键前提：Seal Key / Shamir 分片必须在异地安全保管
```

**必须写明的风险**：若 Seal Key 永久丢失且无分片备份，数据**不可恢复**。这是设计特性而非缺陷。

## 十七、认证与授权

### 17.1 认证方式

| 方式 | 用途 | 版本 |
|---|---|---|
| API Token | 服务间调用 | V1 |
| mTLS | 强身份、K8s 与设备 | V2 |
| OIDC / JWT | 企业身份源对接 | V2 |
| AppRole 类角色 | 机器身份 | V3 |
| TOTP / MFA | 管理员高危操作 | V3 |

**Token 要求**：

```text
CSPRNG ≥ 128 bit 熵
数据库仅存 SHA-256(token) 或 HMAC(token)
支持 TTL、续期上限、吊销、最后使用时间
明文只在创建时返回一次
```

**说明**：Token 是高熵随机值，可用 SHA-256 索引；用户口令**不能**如此处理，必须 Argon2id。

### 17.2 角色

| 角色 | 权限 |
|---|---|
| PLATFORM_ADMIN | 平台级：租户、Seal、系统配置 |
| TENANT_ADMIN | 租户内：密钥、证书、策略、Token |
| KEY_ADMIN | 密钥创建、轮换、吊销、销毁 |
| CA_ADMIN | CA、Profile、签发、吊销 |
| CRYPTO_USER | 使用授权密钥执行密码运算 |
| SECRET_READER | 读取授权秘密 |
| AUDITOR | 只读审计与状态 |

### 17.3 授权判定

```text
输入：Actor + Tenant + Role + Operation + Resource
      + KeyPurpose + KeyStatus + KeyVersion + 请求参数

步骤：
1. 租户匹配（必须一致，否则拒绝）
2. 角色是否具备该操作类别
3. 策略路径匹配与参数约束
4. 密钥/证书状态与用途校验
5. 配额与限流
6. 审计
```

**必须拒绝**：跨租户访问、用加密密钥签名、用吊销密钥操作、SEALED 状态密码操作、超配额、非授权 Profile 签发。

## 十八、审计、取证与合规

### 18.1 审计事件

```text
event_id / tenant_id / request_id
actor / role / operation
resource_type / resource_id / key_version / algorithm
source_ip / result / error_code / duration_ms / created_at
previous_hash / event_hash
```

### 18.2 Hash Chain（AU-02）

```text
event_hash = HMAC(audit_key, previous_hash ‖ canonical_event_json)
```

**要求**：

- Audit Key 与业务密钥分离，由 Master Key 包装；
- Canonical JSON 字段顺序固定；
- 链验证按 event_id 顺序重算，指出首个不一致位置；
- 关键写操作审计失败即失败（AU-09）；
- 大对象只记录长度与摘要，不记录内容。

### 18.3 Merkle 锚定（AU-03）

```text
每 N 条或每 T 分钟计算 Merkle Root
用审计签名密钥签名 Root
可选：写入外部不可篡改存储或第三方存证
作用：支持"某时间点之后无篡改"的外部证明
```

### 18.4 导出与归档（AU-06）

```text
导出：按时间窗/租户/资源导出 JSON 或 CSV
归档：按保留策略轮转，归档文件带链证明
保留：合规保留期可配置，到期安全删除
```

### 18.5 脱敏策略（AU-10）

| 字段类型 | 处理 |
|---|---|
| 明文/密钥材料 | 绝不记录 |
| Token | 记录哈希或前后 4 位 |
| AAD | 记录 `aad_hash` |
| 证书 Subject | 按策略可记录 |
| 私钥路径/文件名 | 不记录 |
| 用户输入原文 | 不记录，只记长度与摘要 |

## 二十、C++ 工程实现要求

### 20.1 RAII 封装

必须包装：`EVP_CIPHER_CTX`、`EVP_MD_CTX`、`EVP_PKEY`、`EVP_PKEY_CTX`、`BIO`、`X509`、`X509_REQ`、`X509_CRL`、`X509_STORE`、`X509_STORE_CTX`、`OSSL_LIB_CTX`。

```cpp
template <typename T, void (*FreeFunc)(T*)>
struct OpenSslDeleter {
    void operator()(T* ptr) const noexcept { if (ptr) FreeFunc(ptr); }
};

template <typename T, void (*FreeFunc)(T*)>
using OpenSslPtr = std::unique_ptr<T, OpenSslDeleter<T, FreeFunc>>;

using EvpPkeyPtr = OpenSslPtr<EVP_PKEY, EVP_PKEY_free>;
using X509Ptr    = OpenSslPtr<X509, X509_free>;
using BioPtr     = OpenSslPtr<BIO, BIO_free_all>;
```

### 20.2 使用 EVP 高层接口

```text
EVP_EncryptInit_ex2 / Update / Final_ex
EVP_DecryptInit_ex2 / Update / Final_ex
EVP_DigestSignInit_ex / DigestSign / DigestSignFinal
EVP_DigestVerifyInit_ex / DigestVerify / DigestVerifyFinal
EVP_PKEY_keygen_init / EVP_PKEY_generate
EVP_PKEY_encrypt / EVP_PKEY_decrypt
EVP_PKEY_CTX_set_rsa_padding / set_rsa_pss_saltlen / set_rsa_mgf1_md
OSSL_PARAM
```

禁止直接访问 OpenSSL 3.x 已弃用的 RSA/EC/DSA 内部结构。

### 20.3 错误处理

```cpp
std::string collectOpenSslError() {
    std::string result;
    unsigned long code = 0;
    char buffer[256];
    while ((code = ERR_get_error()) != 0) {
        ERR_error_string_n(code, buffer, sizeof(buffer));
        if (!result.empty()) result += "; ";
        result += buffer;
    }
    return result;
}
```

- 内部日志记完整错误链；外部只返回映射错误码；
- 调用前 `ERR_clear_error()`；
- 错误对象携带 `request_id` 便于关联。

### 20.4 并发要求

| 项目 | 要求 |
|---|---|

| 公钥/证书缓存 | 只缓存不可变解析结果 |

## 二十八、风险与权衡

| 风险 | 影响 | 应对 |
|---|---|---|
| 范围过大导致长期无成果 | 挫败、无法演示 | 阶段 3 强制冻结并演示；裁剪方案明确 |
| OpenSSL/GmSSL 兼容性坑 | 跨库验签失败 | 进程隔离 + 兼容矩阵 + 显式参数 |
| HSM 无真实设备 | 设备层停留模拟 | KMIP/PKCS#11 用软件模拟器（SoftHSM）验证 |
| 自行设计格式风险 | 互操作差 | 优先采用标准（KMIP/PKCS#11/RFC） |
| 性能优化过早 | 浪费时间 | 先有基准再优化，只优化 profiler 指出的瓶颈 |
| 安全过度承诺 | 面试被追问崩塌 | 文档明确边界与限制 |
| 单一 Seal Key 丢失 | 数据不可恢复 | Shamir 分片 + 异地保管 + 演练 |
| 多租户隔离缺陷 | 数据越权 | 强制 tenant 过滤 + 越权测试 + 审计 |
| C++ 内存问题 | 崩溃/泄漏 | RAII + ASan + 模糊测试 |
| 时间线拉长动力下降 | 项目停滞 | 每阶段可演示 + 里程碑跟踪表 |

**关键权衡**：

1. **自研 vs 复用**：一致性、HA、TLS 一律复用成熟方案，精力投入密钥与证书治理；
2. **功能数 vs 深度**：宁可 79 项 V1 项项扎实，不要 210 项项项半成品；
3. **安全 vs 易用**：默认最安全（不可导出、短 TTL、失败关闭），放宽需显式配置。

## 二十九、面试讲解与简历材料

### 29.1 三分钟版本

> KeyCertHub 是一个用 C++17、OpenSSL 与 GmSSL 构建的企业级密钥与证书管理系统。它通过 Provider 层隔离密码库与密码设备，用 Seal Key → Master Key → Managed Key → DEK 四层模型保护密钥材料，支持密钥全生命周期管理、版本轮换与历史数据解密、信封加密与 Rewrap；同时实现多级 CA、CSR、受控证书 Profile、签发续期吊销、CRL/OCSP 与证书链验证。系统提供 REST、KMIP、EST、OCSP 等接口，支持多租户隔离、策略引擎、防篡改审计、PKCS#11 密码机对接、高可用部署与完整测试体系。

### 29.2 十分钟架构讲解要点

```text
1. 分层架构与信任边界
2. 四层密钥体系与 Seal 状态机
3. 密钥版本与轮换语义（旧数据如何继续解）
4. Provider 抽象与能力协商
5. 证书生命周期与 Profile 受控签发
6. 审计链设计与失败关闭
7. 多租户隔离实现
8. 高可用与灾备取舍
```

### 29.3 必答问题清单

**密码原理**

1. 数据库被拖库后攻击者能拿到什么？

4. 为什么 CBC 必须 Encrypt-then-MAC？

### 29.4 简历项目描述

> 基于 C++17、OpenSSL 3.x 与 GmSSL 设计并实现企业级密钥与证书管理系统 KeyCertHub，通过 `CryptoProvider` 抽象统一封装 AES-GCM、SM4、RSA-OAEP/PSS、ECDSA、Ed25519、SM2/SM3 等密码能力，对外提供 REST/gRPC/KMIP/EST/OCSP 多协议接口。

> 设计 Seal Key → Master Key → Managed KEK → DEK 四层密钥保护模型，实现密钥材料加密落库、用途隔离、状态机、版本轮换、历史密文解密、Rewrap、自动轮换与 BYOK 导入导出，数据库中不保存明文私钥与对称密钥。

> 实现多级 CA、PKCS#10 CSR、受控证书 Profile、X.509 签发/续期/重签、吊销、CRL/Delta CRL、OCSP 与证书链验证，支持 RSA/SM2 双证书体系，并完成 OpenSSL/GmSSL 跨库兼容矩阵测试。

> 使用 RAII 管理 EVP/X509/BIO 资源，设计 `SecureBuffer` 与统一错误模型；通过 GoogleTest、Google Benchmark、libFuzzer、ASan/UBSan/TSan 完成正确性、安全性、并发与性能验证，核心模块测试覆盖率 xx%。

> 实现多租户隔离、HCL 策略引擎、资源级 ACL、API Token/mTLS/OIDC 认证与 HMAC Hash Chain 防篡改审计；支持 PKCS#11 密码机对接与私钥不可导出，并通过 Docker/Helm 完成多节点高可用部署。
